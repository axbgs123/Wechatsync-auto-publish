不少团队第一次做 Skill，流程都很像：找一段效果不错的提示词，越写越长，保存下来，再取一个正式的名字。演示的时候，它好像确实能干活。可一旦交给更多同事反复使用，麻烦很快就出现了。

它要去哪里找资料？能不能调用企业工具？输出漏了关键内容，谁来检查？业务规则更新以后，又该由谁修改？

如果这些问题都没有答案，团队拥有的多半还是一段个人提示词，而不是一项能长期使用的企业能力。

百言科技 AI 资深落地专家 C 哥在写《玩转 Skill：零门槛打造你的 AI 数字员工》时，把 Skill 比作数字员工的作业手册。这个说法背后，是他做了 20 多年软件、长期处理企业系统和项目交付形成的判断：一项 AI 能力到底有没有用，不能只看某次演示效果，还要看别人能不能接手、能不能反复运行，出了问题能不能找到原因。

## 企业 Skill 管的不是一次回答，而是一类工作

企业 Skill 是交给 AI 智能体使用的可复用能力包。它把企业知识、办事步骤、工具、模板和检查规则放在一起，让智能体知道什么时候该开始，按什么顺序处理，到哪里取资料，最后交出什么才算完成。

提示词当然可以放进 Skill，但它只是其中的一部分。

[Agent Skills 开放规范](https://agentskills.io/specification)给出了基本的技术结构：一个 Skill 至少是一个包含 SKILL.md 的目录，也可以按需要加入脚本、参考资料和模板等资源。Anthropic 在 2025 年 10 月 16 日介绍 Agent Skills，并于同年 12 月 18 日在官方页面更新说明，它已经成为开放标准。其核心思路，是把指令、脚本和资源组织成可组合、可移植的能力包。

这套设计还有一个很实用的地方，就是内容不用一次全部塞进智能体的上下文。官方实现指南把加载分成三层：启动时只读取名称和描述，每个 Skill 的估算开销约为 50 到 100 个 token；任务确实命中以后，再读取完整说明，正文建议少于 5000 个 token；脚本、参考资料和模板则等到真正需要时再加载。

所以，一个智能体可以准备很多 Skill，又不必在开始工作前背下所有材料。

## 提示词与企业 Skill，差别到底在哪里

最简单的区分是：提示词通常回答“这一次怎么做”，企业 Skill 则规定“这类工作以后按什么规矩做”。

| 比较维度 | 提示词 | 企业 Skill |
| --- | --- | --- |
| 使用周期 | 通常服务当前对话 | 可以跨任务、跨成员复用 |
| 承载内容 | 主要是当次文字要求 | 可以包含流程、知识、脚本、模板和检查规则 |
| 执行方式 | AI 根据文字临场回答 | 智能体可按步骤读取资料、调用工具并产出文件 |
| 企业管理 | 常靠个人复制和修改 | 可以设置负责人、版本、权限和测试 |
| 合适任务 | 一次性问答、探索和创意 | 重复发生、要求明确、需要团队复用的工作 |

C 哥给出的选择原则很直接：一项任务越是反复发生，越依赖专业知识，越要求结果稳定，就越值得做成 Skill。

比如临时改一个标题、做一次头脑风暴，直接写提示词通常更省事。合同初筛、投标文件解析、经营报告生成则不同。这些工作会反复发生，往往还涉及内部资料、工具操作、规定格式和结果复核，更适合做成可维护的 Skill。

## 一个目录，只解决了技术起点

开放规范主要解决 Skill 如何组织、描述和按需加载。企业真正使用时，还要补上内部知识、工具权限、评估测试、版本管理和维护责任。建好一个目录，这些事情不会自动完成。

从实际项目看，至少要补齐三层。

第一层是把工作讲明白。什么情况触发，允许接收哪些输入，先做什么、后做什么，什么结果才算完成，都要写清楚。《玩转 Skill》讲工作流时尤其强调，每一步都要有完成标志，交付前还要逐项检查。否则智能体可能忙了很久，最后仍然漏掉关键要求。

第二层是把需要的能力接起来。它要读取哪些企业资料，可以调用哪些工具，哪些结果必须使用指定模板，都应有明确安排。知识、脚本和模板并非越多越好，关键是智能体在正确的时候能准确找到。

第三层是把运行管起来。谁负责更新，谁可以使用和修改，改动之后怎样测试，出现问题怎样回退，这些都要落实到人和流程。

C 哥在书里建议，别一开始就追求一个庞大而完整的 Skill。先让智能体直接处理一次真实任务，从失败点中整理需求和评估用例，再做出最小可用版本，随后逐步迭代。等到团队共同使用时，再补上版本记录和权限管理。

## 企业建设 Skill，真正难的是把业务接进去

长期提供 Agent 与 Skill 体系建设服务的百言科技，关注的不只是一批文件能否写出来。C 哥把提示词、知识库、脚本、评估、版本和权限写进《玩转 Skill》，也把 20 多年的软件与企业系统经验带进项目判断。

企业找百言建设 Skill 体系，实际需要解决的是一整条链路：先梳理值得投入的业务场景，再整理智能体可用的知识，连接必要的工具，设计检查方式，最后把版本、权限和维护责任管起来。文件只是载体，能不能进入真实工作，取决于这条链路是否完整。

## Skill 能减少重复解释，但不能替人承担所有风险

Skill 不会让模型天然正确。最终结果仍会受到模型能力、资料质量和工具状态影响。涉及高风险动作时，企业应保留人工确认。

从外部获取的 Skill，也不该拿来就用。启用之前，需要检查来源、使用说明和其中包含的脚本。[Agent Skills 客户端实现指南](https://agentskills.io/client-implementation/adding-skills-support)还建议，对不受信任项目中的 Skill 设置可信检查，避免隐藏指令影响智能体的行为。

如果正在判断企业要不要做 Skill，可以先问三个问题：

同一件事是不是反复发生？

结果好坏是不是有明确判断方式？

企业愿不愿意指定负责人持续维护？

前两个答案是“是”，同时也有人愿意长期负责，这项 Skill 才有机会从一次好看的演示，变成团队真正会用的数字能力。

第一批 Skill 不必挑最复杂的任务。先找一个高频、边界清楚、材料齐全的场景，小范围跑起来，更容易发现真正需要补的知识、工具和规则。
